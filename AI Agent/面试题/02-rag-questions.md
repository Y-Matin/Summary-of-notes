# AI Agent 面试题库 - RAG 系统篇

## 📚 适用对象

- ✅ RAG 算法工程师（必学，优化检索策略）
- ✅ RAG 开发工程师（必学，系统搭建）
- ⏱️ 建议学习时间：算法岗4天，开发岗3天

## 第一部分：RAG 核心原理（必考）

**Q1: 请解释 RAG 的工作原理。与直接对 LLM 进行微调相比，RAG 主要解决了什么问题？有哪些优势？**

- 我：
  - rag 工作原理是：将检索到的与用户提问相关信息，放入系统提示词上下文当中，交给大模型判断，给出用户提问最相关的答案
  - 与 LLM 微调相比，RAG 决绝了大模型幻觉和更新不及时以及相关词语 未理解的问题，成本低。效果好，

**参考回答：**

RAG 是检索增强生成，核心是**先找资料，再依据资料回答**。离线时把文档清洗、切块并建立索引；用户提问后检索相关片段，把片段和问题一起交给 LLM，生成带来源的回答。

它主要解决模型知识过时、缺少企业私有知识，以及回答缺乏事实依据的问题。相比微调，RAG 更新知识更方便、通常不需要重新训练，也更容易追溯来源和控制访问权限。

微调更适合调整模型的行为、风格和任务能力，RAG 更适合补充外部知识，两者可以结合。**RAG 能减少幻觉，但不能保证消除幻觉**，检索和生成都可能出错。

---

**Q2: 一个完整的 RAG 流水线包含哪些关键步骤？请从数据准备到最终生成，详细描述整个过程。**

- 我：
  - 提前将待检索的文档 按照合理的分段逻辑进行切割，然后计算向量化，然后存入数据库中，常见的向量数据库 redis，milvs，当用户提问时，将用户的关键词进行优化补充，向量化计算，找到和提问内容贴近的内容，（多路召回，TopK），放入系统提示词上下文中，和用户提问一起发送给 LLM，LLM 结合上下文和提问题，进行分析，然后给出合理回答。

**参考回答：**

我会分成**离线建库**和**在线问答**两条流程：

1. **采集与清洗**：解析 PDF、网页等资料，必要时做 OCR，去重并保留标题、表格、来源和权限。
2. **切块**：按标题、段落或语义边界拆分，记录原文位置和文档版本。
3. **建索引**：用 Embedding 模型生成向量，也可建立 BM25 关键词索引，支持混合检索。
4. **理解问题**：结合对话历史补全指代，按需改写查询、识别意图或拆分子问题。
5. **召回与筛选**：在权限和业务范围内召回候选片段，融合、去重、重排，保留有效证据。
6. **生成回答**：按 token 预算组装问题、资料和提示词，让模型依据证据回答并标注引用。
7. **校验与维护**：检查结论和引用是否匹配；证据不足时说明限制，并持续评估、增量更新知识库。

整个链路最重要的是：**检索到正确资料、保留必要上下文、让答案有证据可查**。

---

**Q3: 在构建知识库时，文本切块策略至关重要。你会如何选择合适的切块大小和重叠长度？这背后有什么权衡？**

- 难度：⭐⭐
- 岗位：通用
- 标签：#RAG #文档处理 #切块策略

**参考回答：**

我会优先按标题、段落和语义边界切块，再用业务问答集调大小，而不是只按固定字数截断。

- **块太小**：定位精确，但容易把定义、条件和结论拆开。
- **块太大**：上下文完整，但无关信息更多，检索区分度下降，也增加生成成本。
- **重叠太少**：容易丢失跨块信息；**重叠太多**：会增加存储和重复召回。

例如，可以先试每块 300～800 tokens、重叠 10%～20%，这只是实验起点，不是标准答案。表格、代码和完整条款尽量保留结构；也可以用“检索小块、返回父段落”的方式兼顾精度与完整性。

最终结合 Recall@K、回答正确率、延迟和成本选择参数。

---

**Q4: 如何选择一个合适的嵌入模型？评估一个 Embedding 模型的好坏有哪些指标？**

- 难度：⭐⭐
- 岗位：通用
- 标签：#RAG #Embedding #模型选择

**参考回答：**

我会先看业务匹配度：是否支持目标语言、行业术语和文档长度，是否适合检索任务，以及能否满足部署和成本要求。

评估主要看三类指标：

- **检索质量**：Recall@K 看相关资料是否被找回，MRR 看第一个相关结果的位置，nDCG@K 看整体排序质量。
- **工程性能**：编码延迟、吞吐量、向量维度带来的存储与索引成本。
- **业务效果**：在相同切块和检索配置下，对比真实问题的回答正确率，并检查缩写、编号和跨语言查询等难例。

[MTEB](https://arxiv.org/abs/2210.07316) 等公开评测适合初筛，最终仍要用自己的业务数据验证。查询和文档应遵循模型各自的编码规范；不同模型的向量不能直接混用，维度相同也不代表处于同一向量空间。

## 第二部分：检索优化（算法岗重点）

**Q5: 除了基础的向量检索，你还知道哪些可以提升 RAG 检索质量的技术？**

- 难度：⭐⭐⭐
- 岗位：算法岗、开发岗通用
- 标签：#RAG #检索优化 #混合检索
- 公司：字节、阿里（高频）

**参考回答：**

我通常从查询、召回和排序三个环节优化：

- **查询改写与分解**：补全指代、扩展同义词，把复杂问题拆成可检索的子问题。
- **混合检索**：结合 BM25 和向量检索，兼顾编号、术语的精确匹配与语义匹配；可用 RRF 按排名融合，避免直接相加不同尺度的分数。
- **重排**：用 Reranker 对问题和候选片段做更细的相关性判断。
- **上下文补全**：检索到小块后补充父段落或相邻片段，避免证据不完整。
- **过滤与去重**：按权限、版本和时间约束筛选，再去掉重复内容；必要时用 MMR 兼顾相关性和信息多样性。

我会通过对照实验确认收益。尤其要注意：**重排只能优化已召回的结果，无法补回漏掉的资料**。

**Q6: 请解释"Lost in the Middle"问题。它描述了 RAG 中的什么现象？有什么方法可以缓解这个问题？**

- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#RAG #长文本 #优化

**参考回答：**

“Lost in the Middle”指模型处理长上下文时，对开头和结尾的信息利用较好，却容易忽略中间的重要信息。在 RAG 中，即使检索到了正确资料，放在大量片段中间也可能没有被有效利用。这个现象见于[原论文的实验](https://arxiv.org/abs/2307.03172)，具体程度取决于模型和任务。

我会从三方面缓解：

- 先重排、去重和压缩，减少无关上下文。
- 在不破坏逻辑顺序的前提下，把关键证据放到较显眼的位置，并标注来源。
- 对复杂问题分步检索、分步回答，避免一次塞入大量资料。

关键是提高有效信息密度，不能只依赖更大的上下文窗口。

---

**Q7: 在什么场景下，你会选择使用图数据库或知识图谱来增强或替代传统的向量数据库检索？**

- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#GraphRAG #知识图谱 #检索策略

**参考回答：**

当问题依赖**实体关系、多跳推理或全局归纳**时，我会考虑图数据库或知识图谱。例如“某供应商通过哪些公司关联到这个项目”，需要沿关系追踪，单纯寻找相似文本不够。

图检索适合查实体、关系和路径；向量检索适合找到相关描述。实际中可以先定位实体和关系，再检索对应原文，让模型依据证据回答。

对于“这批报告的主要主题是什么”这类全局问题，[GraphRAG](https://microsoft.github.io/graphrag/) 还可以利用图社区及其摘要支持归纳，不只是查询关系路径。

代价是实体抽取、关系维护和更新更复杂，抽取错误也会影响答案。因此，普通文档问答优先采用更简单的检索方案，有明确关系需求时再引入图。

## 第三部分：评估与优化（通用）

**Q8: 如何全面地评估一个 RAG 系统的性能？请分别从检索和生成两个阶段提出评估指标。**

- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#RAG #评估 #指标设计

**参考回答：**

我会把**检索是否找对资料**和**生成是否答对问题**分开评估。

| 阶段 | 主要指标 | 关注点 |
| --- | --- | --- |
| 检索 | Recall@K | 所需证据是否被召回 |
| 检索 | Precision@K | 返回的片段有多少真正相关 |
| 检索 | MRR、nDCG@K | 相关资料是否排在前面 |
| 生成 | 正确性、完整性 | 是否答对，是否覆盖问题要点 |
| 生成 | 忠实度、引用准确性 | 结论是否得到资料支持，引用是否对应 |
| 生成 | 拒答与澄清质量 | 无答案或问题不明确时是否恰当处理 |

此外要看端到端延迟、P95 延迟、单次成本和失败率。评测集应覆盖普通问题、复杂问题、过期资料和无答案问题，并提供参考答案与证据。

**忠实于资料不等于事实正确**：资料本身也可能出错。LLM 可以辅助评分，但需要人工抽检，避免把模型评分当成绝对标准。

**Q9: 传统的 RAG 流程是"先检索后生成"，你是否了解一些更复杂的 RAG 范式，比如在生成过程中进行多次检索或自适应检索？**

- 难度：⭐⭐⭐⭐
- 岗位：算法岗重点
- 标签：#RAG #高级技术 #自适应检索

**参考回答：**

了解，核心是**按问题难度和证据缺口决定何时检索、检索几次**。

- **迭代式 RAG**：先检索一轮，再根据缺失的信息生成下一轮查询，适合多跳问题。
- **自适应 RAG**：根据问题复杂度，选择不检索、单次检索或多次检索。[Adaptive-RAG](https://arxiv.org/abs/2403.14403) 是代表性方法。
- **Self-RAG**：原方法通过训练模型使用反思标记，判断是否需要检索，并评价证据和生成结果；不能简单等同于加一段“自我检查”提示词。[原论文](https://arxiv.org/abs/2310.11511)
- **Agentic RAG**：把检索作为工具，由 Agent 动态选择数据源、改写查询并决定是否继续查找。

这些方法能处理更复杂的问题，但会增加延迟、成本和出错机会。我会设置最大轮数、超时和明确的停止条件，避免反复检索却没有新增证据。

## 第四部分：工程实践（开发岗重点）

**Q10: RAG 系统在实际部署中可能面临哪些挑战？**

- 难度：⭐⭐⭐
- 岗位：开发岗重点
- 标签：#RAG #部署 #工程实践
- 公司：字节、阿里（高频）

**参考回答：**

实际部署中，我会重点关注以下问题：

- **数据质量与更新**：解析错误、重复文档和过期版本会直接影响答案，需要可追踪的增量更新与删除机制。
- **效果稳定性**：检索漏召回、重排误判和模型幻觉，需要通过评测集、引用检查和无答案处理控制。
- **延迟与成本**：Embedding、检索、重排和生成层层叠加，要通过缓存、并发控制和上下文预算优化。
- **权限与安全**：多租户隔离、检索权限和缓存隔离必须由系统执行；外部文档中的指令不能被当作可信操作指令。
- **可运维性**：记录每阶段耗时和证据来源，支持超时、限流、降级以及模型和索引版本回滚。

我的判断标准是：不只是演示能回答，而是持续运行时**答案可靠、权限正确、成本可控、问题可定位**。

**Q11: 了解搜索系统吗？和 RAG 有什么区别？**

- 难度：⭐⭐
- 岗位：开发岗重点
- 标签：#RAG #搜索系统 #对比分析

**参考回答：**

了解，两者共享索引、召回和排序等基础能力，但输出目标不同。

| 对比项 | 搜索系统 | RAG 系统 |
| --- | --- | --- |
| 主要输出 | 文档、链接或片段列表 | 基于资料组织的答案及引用 |
| 核心链路 | 查询 → 召回 → 排序 → 展示 | 查询 → 检索 → 组装证据 → 生成 → 校验 |
| 重点评估 | 相关性、排序质量和检索效率 | 检索质量，以及答案正确性和忠实度 |
| 主要风险 | 漏检、错排、过期结果 | 同样的检索问题，再加上生成幻觉和引用错误 |

RAG 可以复用成熟搜索系统作为检索底座。**向量数据库只是其中一种检索组件，不等于完整的搜索系统或 RAG 系统**。

我了解的开源方案主要有以下几类，选择时会看文档类型、定制程度和运维要求：

| 框架或平台 | 主要侧重 | 我会优先考虑的场景 |

> 面试时，“了解过”和“实际使用过”要区分；项目经历和指标应按自己的真实情况补充。

## 第五部分：RAG 进阶技术（真题补充）

**Q13: 构建向量检索库时如何处理时间衰减对召回的影响？**

- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#时间衰减 #召回优化
- 公司：字节(真题)

**参考回答：**

我会先判断问题是否对时间敏感。新闻、政策和产品版本需要强调时效，基础概念和历史问题则不能一律偏向新文档。

具体可以这样做：

- 保存发布时间、业务生效时间、版本和失效状态，不能只用入库时间判断新旧。
- 对“最新规定”这类问题先过滤有效版本，再在相关候选中加入时间权重。
- 对历史问题按指定时间范围检索，避免拿当前资料回答过去的情况。

例如，重排时可以采用 `综合分 = α × 相关性分 + β × exp(-λ × 文档年龄)`，先统一分数尺度，再按业务调整衰减速度。这个公式只是可选方案，不能让新但无关的文档压过旧但正确的资料。

还要保证召回阶段能找到新文档；如果它没有进入候选集，后续时间加权也无效。

**Q14: RAG中知识库搭建，对知识库的文件文档进行动态增量更新，怎么来避免新旧文档的分布不一致导致的检索偏差问题？**

- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#增量更新 #分布一致性
- 公司：美团(真题)

**参考回答：**

我会先区分：偏差来自**处理流程不一致**，还是新文档本身带来了新的业务内容。正常的知识变化不应该被强行抹平。

- **统一处理规范**：清洗、切块、Embedding 模型版本、查询与文档编码方式，以及向量归一化规则保持一致。
- **正确处理版本**：用文档 ID、版本号和内容哈希识别变更，更新受影响片段，并让失效版本及时退出有效检索范围。
- **模型升级单独迁移**：换 Embedding 模型时建立新索引并重新编码，验证后切换；不能把不同模型生成的向量直接混入同一空间。
- **监测索引与业务效果**：分别检查新旧文档的召回率、排序和难例；如果使用 IVF 等依赖训练的索引，还要判断新增分布是否需要重训或重建。

如果偏差来自新术语或新领域，可以补充关键词检索、术语映射或领域适配，再用评测验证，而不是简单给所有新文档加权。

**Q15: RAG如果有噪声怎么办？**

- 难度：⭐⭐
- 岗位：通用
- 标签：#噪声处理 #数据质量
- 公司：字节、阿里

**参考回答：**

我会先定位噪声来自哪一层，再针对性处理：

- **数据噪声**：页眉页脚、乱码、重复内容和 OCR 错误，在入库前清洗；有价值的表格和结构要保留。
- **检索噪声**：召回了相似但不相关的片段，通过查询改写、业务过滤和重排改善。
- **上下文噪声**：重复或无关信息占满窗口，通过去重、压缩和控制片段数量提高信息密度。
- **证据冲突**：不同来源或版本说法不一致，按有效时间和来源可信度处理，必要时明确说明分歧。

如果处理后仍没有足够证据，就澄清或说明无法确认。过滤不能只追求“干净”，还要监控召回率，防止把真正需要的资料一起删掉。

**Q16: 讲一下BM25算法原理**

- 难度：⭐⭐
- 岗位：通用
- 标签：#BM25 #稀疏检索
- 公司：字节、阿里(高频)

**参考回答：**

BM25 是一种基于关键词匹配的相关性评分算法，通常配合倒排索引检索。可以从三个因素理解：

- **词频**：查询词在文档中出现越多，通常越相关，但收益会逐渐饱和，避免堆词刷分。
- **逆文档频率（IDF）**：越少见的词，区分能力通常越强，权重越高。
- **文档长度归一化**：长文档更容易出现查询词，需要修正长度带来的优势。

常见评分形式是：

```text
score(q, d) = Σ IDF(t) × [f(t,d) × (k1 + 1)]
                       / [f(t,d) + k1 × (1 - b + b × |d| / avgdl)]
```

其中，求和遍历查询词；`f(t,d)` 是词频，`|d|` 是文档长度，`avgdl` 是平均文档长度；`k1` 控制词频饱和，`b` 控制长度归一化强度。[Elasticsearch 文档](https://www.elastic.co/docs/reference/elasticsearch/index-settings/similarity)

BM25 适合编号、产品名和术语等精确匹配，但对同义改写的理解较弱，所以 RAG 常将它与向量检索结合。中文场景还需要注意分词质量。

**Q17: 是否做过意图识别？如果要做意图识别，可以怎么实现？**

- 难度：⭐⭐
- 岗位：开发岗重点
- 标签：#意图识别 #NLU
- 公司：字节、阿里

**参考回答：**

如果要做意图识别，我会先定义业务意图，例如知识问答、数据查询、业务操作、闲聊和无法判断，再抽取对象、时间等必要参数。

实现方式可以按复杂度选择：

- **规则或关键词**：简单、低延迟，适合边界清晰的固定指令。
- **分类模型或 Embedding 匹配**：适合意图相对稳定、需要较高吞吐的场景，有标注数据时可训练分类器。
- **LLM 结构化分类**：适合复杂表达或多意图问题，让模型返回意图与参数，并由程序校验。

我会先路由，再校验参数；意图不明确时澄清。评估看各意图的 Precision、Recall、F1 和混淆矩阵，特别关注把普通问答误判成执行操作的情况。

**意图识别只决定走哪条流程，不代表用户已经获得操作权限**。

**Q18: 介绍检索做的优化，具体追问子问题分解怎么做，有没有做意图识别？**

- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#检索优化 #子问题分解
- 公司：字节(真题)

**参考回答：**

如果让我设计检索优化，我会先分析失败样例，判断是问题理解错误、召回遗漏，还是排序和上下文组织不合理，再选择对应方案。

对子问题分解，我会这样做：

1. **识别意图和复杂度**：简单问答直接检索；比较、跨文档或多跳问题再分解。
2. **生成可检索子问题**：保留原问题的对象、时间和约束，并标记子问题之间的依赖。
3. **按依赖执行**：独立子问题可并行；依赖前一步结果的问题顺序检索。
4. **合并证据再回答**：去重、重排，并检查各子问题是否都有证据，避免遗漏原始要求。

例如“对比 A、B 产品的退款期限和手续费”，可以分别检索 A、B 的退款规则，再按相同维度对比。若问题是“这家公司的创始人毕业于哪里”，则先确定创始人，再查教育经历。

我会限制分解数量和轮数，用完整问题的回答正确率验证收益，而不是只看子问题有没有返回结果。

**Q19: 在RAG里的"召回-过滤-生成"三段式 pipeline能细讲一下吗？**

- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#Pipeline设计 #三段式
- 公司：字节(真题)

**参考回答：**

这三段的目标分别是：**召回找全候选，过滤留下有效证据，生成组织答案**。

1. **召回**：理解查询，在用户权限和业务约束内，通过向量、关键词等方式检索较多候选，再融合结果。主要关注 Recall@K，避免关键证据缺失。
2. **过滤**：去重、排除失效版本和无关内容，用重排模型细排，必要时补充上下文，按 token 预算选出证据。权限应在检索阶段生效，不能等生成时再由模型判断。
3. **生成**：把问题与证据交给 LLM，要求回答要点、标注来源；证据不足时说明限制，并检查结论是否得到引用支持。

例如，可以先召回 50 个片段，筛选后保留 5～8 个用于生成，具体数量需要评测。排查时先看“证据有没有召回”，再看“过滤有没有误删”，最后看“模型有没有正确使用”。

**Q20: 介绍一下function calling和MCP**

- 难度：⭐⭐
- 岗位：开发岗重点
- 标签：#Function Calling #MCP
- 公司：字节、阿里

**参考回答：**

**Function Calling** 是模型通过结构化格式提出工具调用，例如返回 `search_docs(query="退款规则")`。应用校验参数和权限后执行工具，把结果交回模型，再由模型继续回答；模型本身通常不会直接执行本地函数。[工具调用文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)

**MCP（Model Context Protocol）** 是 AI 应用连接外部工具和数据源的标准协议。Host 中的 Client 与 Server 通信，Server 可以暴露工具、资源和提示词，减少每个应用重复编写接入逻辑。[MCP 架构文档](https://modelcontextprotocol.io/docs/learn/architecture)

两者可以配合：应用通过 MCP 发现搜索工具，将工具描述交给模型；模型通过 Function Calling 选择工具和参数；应用再通过 MCP 调用并回传结果。

可以理解为：**Function Calling 解决模型如何表达工具调用，MCP 解决应用如何标准化连接工具服务**。权限校验、超时和错误处理仍需要应用与工具服务落实。

**Q21: 在高并发查询 Agent 系统中，你会如何优化召回和生成阶段的延迟？**

- 难度：⭐⭐⭐
- 岗位：开发岗重点
- 标签：#高并发 #延迟优化
- 公司：字节(真题)

**参考回答：**

我会先分解链路耗时，重点看 P95 延迟和排队时间，再分别优化召回与生成。

- **召回阶段**：并行执行独立的关键词与向量检索；使用适当的近似最近邻索引和预过滤；缓存高频查询的 Embedding 与检索结果；只对有限候选做重排。
- **生成阶段**：去掉重复证据、压缩上下文并限制输出长度；按任务难度选择模型；使用流式输出降低首字等待时间；自部署时可利用连续批处理和 KV Cache。
- **并发控制**：设置队列、限流、超时和背压，避免上游无限请求压垮下游；独立任务可以并行，有依赖的任务仍需顺序执行。
- **缓存安全与失效**：缓存键包含租户、权限范围及索引版本，知识更新或权限变化后及时失效。

优化时同时检查 Recall@K 和回答正确率。**流式输出主要改善首字延迟，不等于完整答案生成更快**；不能为了低延迟把必要证据删掉。

**Q22: 如果让 agent 调用搜索引擎，如何避免无关结果影响回答？**

- 难度：⭐⭐
- 岗位：通用
- 标签：#结果过滤 #相关性
- 公司：字节(真题)

**参考回答：**

我会把搜索结果当作候选证据，经过筛选后再交给模型，而不是直接使用搜索引擎前几条摘要。

1. **明确查询范围**：保留对象、时间和必要约束，按需改写或拆分查询，优先可靠来源。
2. **获取并清洗正文**：必要时读取原文，去掉广告、导航和重复内容，同时记录网址、日期及来源。
3. **判断相关性**：用规则或重排模型检查是否真正回答问题，并筛除不适用的旧版本和重复报道。
4. **核对证据**：关键结论优先核对原始来源，存在冲突时说明差异，避免仅凭摘要下结论。
5. **约束生成**：只将有效片段放入上下文，要求引用；证据不足时继续查找、澄清或说明无法确认。

另外，网页中的指令属于外部内容，不能让它改变 Agent 的行为或触发未授权工具调用。最终还要检查答案是否实际得到引用支持。
